# 测试、证据、问题闭环

## 测试矩阵

- 各 `REQ-ID` 至少映射一个验证点和一个可判定验收预期。
- 每个 API 明确：方法/路径/依赖环境、token 权限类别、入参约束、正例、必填/格式/空值/边界异常、资源不存在、权限不足、重复提交/幂等、并发、分页排序；不适用要说明。
- 数据库验证：约束、空值、索引、读写一致性、事务回滚和方言兼容；外部依赖验证：超时、降级、重试、重复投递。
- 模块测试先跑，最终整体验证包含跨模块集成与回归，不能仅凭单测通过宣称“全量”。

## 严格测试证据

每个测试用例填：`CASE-ID`、`REQ-ID`、执行时间、环境/分支/commit、命令/调用方式、HTTP 方法/URL、请求 headers（删去密钥）和 JSON、预期、实际 HTTP 状态 + JSON、数据库侧观察（如需）、结果 `PASS/FAIL/BLOCKED/NOT_RUN`、日志/报告相对路径、测试人或执行代理。

请求/响应必须标明来源：`实测采集（脱敏）` 或 `示意（未执行）`。禁止用 `示意` 伪装实测；线上敏感数据脱敏后保留结构，不提供真实 token、手机号、证件号、工号等个人敏感内容。

异常状态：
- `FAIL`：测试确实执行但不符合预期；需关联 `BUG-ID`。
- `BLOCKED`：未能执行，例如数据库/联调服务/账号不可用；写明环境问题和补测条件。
- `NOT_RUN`：本轮尚未尝试执行；不要计算为通过。

## 缺陷处理循环

1. `BUG-001`：复现入口、所属模块、受影响 REQ、预期/实际、影响等级、日志/SQL 栈及根因已验证证据。
2. 先确认原因，提出最小修复方案、具体文件/方法、潜在副作用与覆盖测试。
3. 如引起新 DDL、对外接口、业务边界、鉴权或架构变化，记录 `CR-ID` 并审批；普通已批范围内的 bug 修复可直接实施，但先写在问题单。
4. 修改代码后**重跑原失败用例**和受影响的模块单测/回归；附新的请求/响应实例和测试时间。
5. 更新 issue 状态：`OPEN → TRIAGED → FIXED → VERIFIED → CLOSED`；没有复测证据最多 `FIXED`，不可标 `CLOSED`。

## 测试总结

总数按用例唯一 ID 统计：`PASS + FAIL + BLOCKED + NOT_RUN = 总用例数`。接口覆盖与需求覆盖分别统计，不用纯通过率遮盖 BLOCKED。报告必须给出“本次可支持的结论、未覆盖/风险、剩余问题及交付状态”；列出自动化测试、手工/模拟数据测试的区分。无环境时产出**测试计划/预期示例**，标题明确标 `未执行，不是测试报告通过结论`。
