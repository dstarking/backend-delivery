# 逐模块实施计划与编码准则

## 计划生成步骤

1. 只读取**已批准的方案版本**与对应模块的 `REQ`，检查该模块依赖是否满足。
2. 定位现有源码及近邻模块，逐一核对真实路径、类名、接口、DTO/VO/Entity、Mapper/Repository、测试框架、配置和 SQL；找不到即标拟新增/待核实。
3. 罗列每个接口：HTTP 方法、路径、鉴权、幂等、请求字段/类型/约束/枚举、统一返回模型/示例、错误码、状态码、关联需求 ID。
4. 罗列每个变更文件的操作（新建/修改/复用/不改）、职责、关键实现点、依赖、潜在兼容风险。**每个计划单独 `.md`**，不可把所有模块混为一个大清单。
5. 给出可落地的分批实现步骤：DB/基础模型→Service→API→校验/测试→联调；说明每步验证命令与失败回滚方式，拆出完成定义。
6. 设置本计划 `WAITING_APPROVAL`，总结用户需要核对的内容，在用户明确批准**这份计划的版本**之前不得编码。

## 编码原则

- 正确性、证据、可维护性、简洁和最小化变更优先；不引入未批准的新业务能力。
- 保持既有分层、类型命名、异常/响应体系、依赖注入、日志规范、SQL 风格、校验注解/错误码和事务规范。禁止臆造“统一规范”。
- DTO、VO、Entity 等字段加含义注释；当值有固定枚举时逐一写明含义、单位和默认值；公共方法及业务方法写作用注释，复杂方法说明参数、返回和异常语义。新增注释必须准确而非装饰。
- 用户指定的 Java 排版约束：**方法结束到下一个方法之间保留两行空行**（遵循现有项目 formatter 可行性）；若自动格式化与该要求冲突，应展示实际差异、请用户确认优先顺序，不绕过团队强制检查。
- 数据库层使用参数化 SQL，核对空值、跨方言兼容与分页统计。任何新索引/表先走方案确认与数据库变更授权。
- 修改前保存 `git status`/diff，修改后逐项核对计划和实际 diff；保护用户原有改动，不擅自重置、提交或推送。
- 每个阶段运行可行的最小验证（编译、静态检查、单测、接口）并写真实结果；测试失败不得掩盖。

## 过程文档更新

计划中的“文件清单”是**预计**，开发结束追加“实际改动文件 + 摘要 + 验证记录 + 偏差原因”。若新增受影响模块/契约变更，先更新方案并依据 `01-workflow-and-gates.md` 的再审批规则决定是否停下。

## 防止过度工作

模块开发结束后只做其验收所需的测试和文档更新，不主动升级依赖、大规模重构、改无关模块、替换框架或自动上线。单模块质量验收不能代替最终全量回归。
